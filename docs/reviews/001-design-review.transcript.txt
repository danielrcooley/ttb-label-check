# Architecture v2: built to survive a hostile reviewer
_2026-09-03. Supersedes the architecture section of PLAN.md where they differ._

## 0. Two corrections from re-reading the brief

1. **A COLA application is a set of images, not one.** The government warning is almost always on
   the BACK label. Brand, class/type, ABV and net contents are on the FRONT. A tool that accepts
   one image per application will report "warning missing" on every front label and get laughed
   out of the room by Dave. So the unit of work is an *application* with one or more images
   (front, back, neck, strip). OCR lines are merged across images before any check runs, and
   every finding says which image it came from.
2. **Pairing is many-to-one, not one-to-one.** In a 300-image importer dump, several photos belong
   to the same application. So pairing is "each image goes to its best-scoring application row
   above a threshold", not a one-to-one assignment. Greedy with a threshold is both simpler and
   more correct here than the Hungarian algorithm.

## 1. The invariant: OCR once, reason many times

Three separable operations, each its own endpoint, each independently testable:

| Step | Endpoint | Cost | Input | Output |
|---|---|---|---|---|
| Extract | `POST /api/extract` | heavy (OCR) | one image | OCR lines with boxes + confidence, extracted candidate fields, image quality score, timing |
| Pair | `POST /api/pair` | light (CPU, ms) | N extractions + M application rows (JSON) | image -> row assignment with confidence, unpaired lists |
| Compare | `POST /api/compare` | light (ms) | one application row + its extractions | per-field checks, warning checks, verdict, recommendation |
| Verify | `POST /api/verify` | heavy | image(s) + row in one call | extract + compare, for the single-label screen |

Why this matters at scale: the expensive step is idempotent and stateless per image. The reasoning
steps operate on small JSON and can be re-run instantly when the agent edits a field or re-pairs
an image. A 1000-image batch does 1000 extracts, one pair call, and up to 1000 compare calls
that each take under a millisecond and can be sent in one bulk request.

## 2. Batch execution model: client orchestrates, server stays stateless

**Decision: the browser drives the batch.** It holds the File handles (lazy, not in memory), sends
images to `/api/extract` through a small promise pool (concurrency 3), and renders results as they
stream back. The server never holds more than a handful of images in RAM and never writes one to
disk.

Rejected alternative: server-side job queue (upload everything, poll a job id). It needs state
(in-memory dies on restart, multi-replica needs Redis), holds up to several GB of images
server-side, contradicts "we're not storing anything", and turns a one-week prototype into an
infrastructure project. It is the correct production evolution (Azure Blob + Queue + scale-out
workers) and is documented as such, not built.

Consequences we get for free:
- Backpressure is natural. The client only has 3 requests in flight.
- Cancel is trivial (AbortController). Resume is trivial (files are still in the browser).
- Progress and ETA are exact (moving average of per-image times).
- Horizontal scaling is trivial: no shared state, so two containers double throughput.
- A closed tab costs the server nothing.

## 3. What happens when someone throws 1000 at it

Design targets, to be measured and PUBLISHED in the README under "Limits and load test":

| Vector | Design response |
|---|---|
| 1000 images through the UI | Streams results, pagination at 50 rows, thumbnails only for visible rows (object URLs revoked on page change), ETA shown, cancel/resume, warn on tab close. Expected on 2 vCPU: ~2 labels/s, so 1000 in about 8-10 minutes with the agent reviewing finished rows the whole time. |
| A script firing 1000 concurrent requests at the API | Global OCR semaphore = vCPU count. Per-client in-flight cap (4). Beyond that: immediate `429` with `Retry-After`, never a queue that grows without bound. `/api/health` bypasses the semaphore so it always answers. The client retries 429/503 with backoff. |
| Batch starving an interactive user | Two semaphores: interactive `/api/verify` gets full CPU; `/api/extract` (batch) gets CPU minus one, minimum one. Batch can never take the last core. |
| One 80 MB, 12000x12000 image | Content-Length checked before reading. Chunked-read cap at 10 MB. Pillow decompression-bomb guard at 40 MP. Clear message: "Image too large, resize below 10 MB / 40 MP." Then downscale to 1600 px longest side and drop the original immediately. |
| Non-image files, corrupt files, zero bytes, SVG, PDF, HEIC | File-signature sniffing (not extension). Accept PNG, JPEG, WebP, TIFF, BMP. Reject SVG (script risk), PDF and HEIC with a specific "convert to JPG or PNG" message. Client pre-checks size and type so bad files never leave the browser. Every rejection is per-file and non-fatal to the batch. |
| Filenames: unicode, path separators, duplicates, `<script>` | Filenames are display-only, rendered with `textContent`, never used as paths. Duplicates get a stable per-batch id. |
| Huge CSV, malformed rows, formula injection | Server parses with Python `csv`, max 5000 rows / 2 MB, per-row validation errors returned (not a whole-file failure). Flexible header matching (`brand`, `Brand Name`, `brand_name`). On export, cells starting with `= + - @` are prefixed with `'` so Excel cannot execute them. |
| Slow image that takes forever | Every request carries a deadline (6 s soft). Preprocessing variants are attempted only while budget remains and confidence is still low. Response includes a `timing` breakdown and a `Server-Timing` header. |
| Native-code crash on a pathological image | OCR runs in a bounded thread pool with per-thread engine instances. Documented hardening step for production: process pool for crash isolation. |
| Refresh mid-batch | Nothing is stored server-side by design. UI warns before unload and offers "export decisions now". Documented as intentional. |
| Adversarial matching inputs | Unicode NFKC (fullwidth letters), casefold, apostrophe/quote family unification, whitespace collapse, punctuation strip. ABV: `45%`, `45.0%`, `45 % ALC/VOL`, `ALC. 45% BY VOL.`, proof-only labels (`90 PROOF` -> 45%). Net contents: mL, ml, cL, L, fl oz (29.5735 mL) with 1% rounding tolerance. OCR confusables (0/O, 1/I/l, 5/S) folded before scoring, never before display. |

Throughput is published as a measured number from `tools/loadtest.py` (httpx + asyncio, prints
p50/p95/max, error histogram, labels/minute) run against the deployed host. When the reviewer
stress-tests, the numbers they get should match the numbers we wrote down.

## 4. Concurrency model inside the container

- Single uvicorn process. asyncio event loop for I/O, a `ThreadPoolExecutor` sized to vCPUs
  for OCR. ONNX Runtime and OpenCV release the GIL during inference, so threads use all cores.
- One OCR engine instance per worker thread (thread-local), ORT `intra_op_num_threads=1` and
  `OMP_NUM_THREADS=1` so N sessions do not oversubscribe N cores.
- Models loaded at startup (baked into the image at build time, no download at runtime, which
  also satisfies the firewall constraint). First request is warm. Health reports `warm: true`.
- Memory budget: ~150-250 MB per engine instance + ~60 MB per in-flight image after downscale.
  2 vCPU / 2 GB is comfortable. 1 vCPU / 1 GB works.

## 5. Domain rules encoded (with citations for the README)

- Health warning text and format: 27 CFR Part 16 (16.21 text; 16.22 type size and legibility).
  Checks: present, exact wording (OCR-tolerant similarity with diff shown), `GOVERNMENT WARNING:`
  all caps, bold (stroke-width heuristic vs body text), relative size (warning text height vs
  brand text height, flagged if suspiciously small; physical mm cannot be measured from a photo
  without scale, and we say so).
- Beverage-type-aware requiredness: spirits (27 CFR Part 5) ABV required; wine (Part 4) ABV may
  be replaced by "Table Wine"/"Light Wine" for 7-14%; malt beverages (Part 7) ABV optional
  federally. Simplified deliberately; documented.
- The check is "label says what the application says", exact. Lab tolerance rules for actual
  alcohol content vs stated (5.65 / 4.36 / 7.65) are out of scope and documented as such.
- Case-only differences (STONE'S THROW vs Stone's Throw) are a Match with a note, never a
  Mismatch. Anything the fuzzy layer accepted is "Needs review", shown with a word diff.
- The tool recommends. The agent decides. Three states per check, three verdicts per
  application, decision buttons per row, exported decisions CSV. No auto-approval anywhere.

## 6. Security posture (real, cheap, documented)

- Access gate: `ACCESS_CODE` env. Set -> USWDS sign-in page, signed HttpOnly cookie. Unset ->
  open, header shows "Demo mode: sign-in disabled. No data is stored." Production path documented:
  Entra ID SSO with PIV/CAC. Not faked.
- Headers: CSP `default-src 'self'; img-src 'self' blob: data:; frame-ancestors 'none'`,
  `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, HSTS behind TLS.
- Container: non-root user, read-only root filesystem with a writable `/tmp`, no shell tools
  needed at runtime, pinned dependencies, `pip-audit` and `ruff` in CI.
- Logging: request id, sizes, timings, status codes. Never label text, never filenames.
- No persistence of any kind. Verified by the read-only filesystem.

## 7. Frontend

- USWDS 3 (self-hosted CSS, Public Sans, icon sprite). No CDN, no external requests at all.
- Vanilla ES modules with a tiny store. No build step. Small enough for a reviewer to read in
  one sitting, which is a feature.
- Screens: **Check a label** (drop one or more images for one application, fields form,
  "Load sample" button that fills the Old Tom Distillery example with bundled images, results
  checklist, click a finding to see the highlight on the image) and **Batch** (drop many images
  or pick a folder, optional CSV with downloadable template, live table, filters "Needs
  attention / Ready / Unpaired", pagination, per-row decision buttons, export).
- Accessibility: USWDS components, 44 px targets, visible focus, `aria-live` for results and
  batch progress, icon + word + color for every status, honors reduced motion and high contrast.
  Section 508 named explicitly in the README.
- Banner: "PROTOTYPE. Not an official U.S. Government system. No data is stored." No seals.

## 10. Re-review additions (second pass over the brief, 2026-09-03)

Product and UX
- **Jenny's printed checklist is the results UI.** Same order she recites: brand, ABV, warning,
  then the rest. Say so in the README; it is the most literal form of "attention to requirements".
- **Print view.** Dave prints his emails. A clean print stylesheet and a "Print report" button
  give agents a review record for the file. Cheap, real, and a wink the reviewers will catch.
- **Branding slot, no seal.** `AGENCY_NAME` / `AGENCY_LOGO` config renders in the header when set;
  empty in the public demo. One line in docs: official marks omitted from a public prototype
  (31 U.S.C. 333); the agency drops its mark in at internal deployment. README acknowledges
  "prepared for the DO A.I. Engineering Coordination Division take-home" in plain text.
- **Explicit pairing beats fuzzy pairing.** CSV template gets an optional `images` column
  (filenames, `;`-separated). If present, pair by filename; otherwise fuzzy. Each row shows
  which method paired it and the confidence.
- **Keyboard triage** (A approve, R reject, F flag, J/K move) for Jenny-type power users.
  Discoverable via a "?" hint, never required. Day 5 if time allows.
- **First-run path is sacred.** Open URL -> "Load sample" -> result in under 3 s, with the
  highlight overlay visible. This is the reviewer's first 10 seconds.

Integration (the brief says "integration decisions" explicitly)
- **OpenAPI at `/api/docs`, self-hosted.** FastAPI's default Swagger UI pulls from a CDN, which
  breaks behind Marcus's firewall and violates our no-external-assets rule. Vendor the Swagger
  UI bundle (or serve `openapi.json` + a short API.md if size becomes a concern). The API is
  how a .NET COLA would consume this; say that next to the docs link.
- **Plain HTTPS request/response only.** No WebSockets, no Server-Sent Events. Restrictive
  government proxies drop both. Batch streaming is achieved by many small requests, which is
  also what keeps the server stateless. State this as a deliberate choice.
- **Locked-down reviewer machines.** Assume Edge on a managed Windows box. ES2020 only, no
  Chromium-only file-system APIs (`webkitdirectory` input for folders, not `showDirectoryPicker`),
  no WebGL, works with third-party cookies blocked, works on a phone.
- **Path to production section** in the README (Marcus: "inform future procurement decisions"):
  Entra ID + PIV auth, Azure Government hosting, Blob + Queue for true async batch, retention
  policy, audit logging, model versioning and evaluation gates, VPAT/Section 508 conformance,
  COLA integration through the same API. Half a page, no more.

Domain and accuracy
- **27 CFR 16.22 also says the REST of the warning may NOT be bold.** (Verify on eCFR before
  coding.) That turns the stroke-width heuristic into a two-sided check: anchor bold, body not
  bold. An all-bold warning is itself a finding. Also in 16.22: separate and apart from other
  text, readily legible, contrasting background, minimum type size by container size, max
  characters per inch. We check size relatively and contrast cheaply (luminance of text vs
  background inside the warning box); the rest is listed as "not checked" in LIMITS.md.
- **Diacritics.** NFKD + strip combining marks before comparison (Château vs Chateau), never
  before display.
- **Orientation.** EXIF transpose first. If mean confidence is low, try 90/180/270 rotations
  inside the budget. RapidOCR's angle classifier handles upside-down lines, not sideways images.
- **Zoom pass for small labels in big photos.** If detected text is tiny relative to the frame

## 13. Fifth pass: implementation traps and federal-reviewer signals (2026-09-03)

Traps that would produce a visible bug
- **Coordinate mapping.** Preprocessing variants (downscale, deskew rotation, zoom crop, PDF
  render) change the pixel space. Every variant carries an affine transform back to the
  ORIGINAL image; OCR boxes are mapped back before they leave the server. Otherwise highlights
  and evidence crops land in the wrong place exactly when the harder variant wins, which is the
  moment a reviewer is watching most closely. Unit-tested with synthetic transforms.
- **Dark labels.** Many spirits labels are black or dark with light or gold text. Add an
  inverted-polarity variant to the preprocessing set (tried when confidence is low). The contrast
  heuristic must be polarity-agnostic.
- **Hyphenated line breaks** in the warning ("preg-" / "nancy"): join a trailing hyphen with a
  lowercase continuation before comparison. Missing-space anchors ("GOVERNMENTWARNING:") are
  matched by fuzzy anchor detection on normalized text.
- **Uncertain heuristics never say "Fail".** Caps, bold, size, contrast, standards of fill,
  beverage-type inference: any heuristic finding is "Needs review" with the evidence crop and
  the rule cited. Only clear text and numeric mismatches are "Mismatch". Title-case detection
  says "Appears to be title case (rejection criterion, 27 CFR 16.22). Confirm." The agent
  resolves it in one glance at the crop. This is the rule that keeps the false-alarm rate low
  and Dave's trust high.
- **Client backoff on 429** is global, not per request: shrink the pool by one on a 429, grow it
  back slowly. Prevents a 429 storm from a 1000-item batch. Per-item retry with jitter, max 3,
  then a visible "Retry" button on the row.
- **CSV from Excel**: handle UTF-8 BOM, fall back to cp1252, sniff `;` delimiters, accept
  decimal commas in numbers ("0,75 L"). Net contents parser also accepts pint/quart/gallon.
- **Readiness gating.** Models load at startup; the health endpoint reports `ready: false` until
  warm and the platform's startup probe waits for it. No cold requests hit a half-loaded engine.
  Azure Container Apps needs `minReplicas: 1` (default is 0 and would reintroduce cold starts).
- **Versioned API** (`/api/v1/...`) and every response carries `engine`, `model_version`,
  `request_id`. Auditability for free.

Federal-reviewer signals (cheap, on theme)
- **SBOM in CI** (CycloneDX via `cyclonedx-bom`) published as a build artifact, plus `pip-audit`.
  Executive Order 14028 made SBOMs a federal procurement expectation; one CI step earns the line.
- **Hash-pinned lockfile** (`pip-compile --generate-hashes`) used by the Dockerfile with

- **Access gate brute-force protection**: constant-time compare, 5 attempts per minute per client.

## 2. Architecture (recommended)

**Stack: Python 3.12 + FastAPI backend, local OCR, vanilla HTML/CSS/JS frontend, one Docker container.**

Why Python: it is Daniel's primary language (StoreXray), it is the expected language for an
AI engineering role, and the OCR/image ecosystem is strongest there.

Why one container with a static frontend: one URL, no build step, no CDN, works behind a
strict firewall, trivially deployable anywhere including Azure.

### OCR engine decision (spike on Day 0)
- **Primary candidate: RapidOCR (ONNX Runtime port of PaddleOCR).** Pure pip install, ~15 MB
  of models, strong on scene text (angles, decorative fonts, glare), returns text boxes with
  confidence. Identical behavior on Windows dev and Linux container. Typical CPU time 0.5-2 s.
- **Fallback: Tesseract 5 via pytesseract.** Battle-tested, but weaker on stylized brand
  fonts and photos, and needs a system binary.
- Decision rule: run both on the same 10 synthetic + 5 photo labels, compare accuracy and
  wall time. Pick one. Keep an `OcrEngine` interface so the choice is a one-line swap and
  so the optional cloud provider slots in cleanly.

### Pipeline (per image)
1. Validate upload (type, size cap ~10 MB, decode). Downscale longest side to ~1600 px.
2. Preprocess variants: (a) as-is grayscale, (b) CLAHE contrast + denoise, (c) deskewed.
   Run OCR on variants in a small thread pool; keep the read with the best mean confidence.
   Budget guard: stop early if the first variant is already high-confidence.
3. Field extraction from OCR lines:
   - ABV: regex for `NN% Alc./Vol.`, `NN% ABV`, `ALC. NN% BY VOL.`, proof. Parse to float.
     Cross-check proof = 2 x ABV when both present.
   - Net contents: regex for mL / ml / L / cL / fl oz; normalize to mL.
   - Government warning: find the `GOVERNMENT WARNING` anchor, gather following lines until
     "health problems." Reassemble, compare to canonical text.
   - Brand and class/type: fuzzy search of the application value against OCR lines and
     line-pairs (brand names often wrap). Return the best-matching span and its score.
4. Matching with three outcomes per field:
   - **Match**: exact after normalization (NFKC, casefold, apostrophe/quote unification,
     whitespace collapse, trailing punctuation strip). Note when only case differed.
   - **Needs review**: fuzzy score above threshold (rapidfuzz, ~88-92) but not exact. Show a
     word-level diff. Common cause is OCR noise, so we say that.
   - **Mismatch** or **Not found**: below threshold or no candidate.
5. Warning checks: present / exact wording / anchor all-caps / anchor bold (heuristic) /
   relative size vs body text (flag if the warning is suspiciously tiny).
6. Overall verdict: "All checks passed", "Needs agent review", "Issues found". Plus elapsed ms.

Documented as a heuristic with its failure modes (all-bold labels, extreme fonts).

## 4. Technical risks the plan underestimates

1. Decorative OCR: confidence is not field accuracy, and expected-value fuzzy search can conceal bad OCR. The Day-0 bake-off needs curved, condensed, outlined, gold-on-black, low-contrast, and mixed-case brands; report exact field recall, false matches, and latency—not mean OCR confidence.
2. Python wheels: ARCHITECTURE inherits Python 3.12 from PLAN; keep it. Enforce `requires-python ==3.12.*`, build Linux/amd64 in CI, and lock RapidOCR, ONNX Runtime, OpenCV, Pillow, and PDFium from that environment. Do not let a Windows Python 3.13 workstation define the lock.
3. ORT concurrency: `intra_op_num_threads=1` and `OMP_NUM_THREADS=1` may not disable all inter-op/provider pools. Verify actual process thread count and throughput at concurrency 1/2/3; a semaphore limits requests, not internal ORT threads.
4. Engine memory: one complete RapidOCR engine per worker may duplicate three model sessions. Measure resident memory after warm-up and under two simultaneous images before asserting that 1 GB works.
5. Coordinate mapping: preserve quadrilaterals, not only axis-aligned boxes; compose EXIF mirroring, rotation, crop, resize, deskew, and PDF-page transforms. Return normalized coordinates in one canonical oriented-image space and test all eight EXIF orientations plus CSS `object-fit`.
6. Client-side evidence crops may disagree with server orientation because browsers decode EXIF differently. Generate the displayed preview through the same canonical orientation or return a canonical preview asset.
7. USWDS without a build step is viable only by vendoring compiled `dist` CSS, JS, fonts, and images with their relative paths intact. Test sprite references, font URLs, CSP behavior, component JavaScript, and asset licensing; do not copy SCSS expecting it to work directly.
8. Azure Container Apps: explicitly configure external ingress, `targetPort`, CPU/memory pair, `minReplicas: 1`, startup/readiness/liveness probes, model-startup allowance, registry access, secrets, and revision traffic. Verify the configured cost instead of repeating the “~$10” estimate.
9. The §3 six-second deadline is per image, while Sarah’s expectation is results per application. A normal front/back application may run two OCR jobs serially or contend with batch work. Publish application-level p50/p95 under concurrent load.
10. Multipart limits are easy to apply after buffering. Enforce aggregate and per-file caps while streaming; multi-image `/verify` must not admit N × 10 MB unchecked.
11. Browser batch “resume is trivial” is overstated. It works only while the tab and file objects survive. A refresh loses extraction, pairing, notes, and decisions; state this plainly and test unload/export behavior.
12. Pairing is both ambiguous and potentially \(N \times M\). A warning-only back image may have no useful match signal. Require explicit/manual pairing before treating a grouped application as ready.
13. PDF rendering multiplies input size and exposes native parsing code. If retained, cap pages, rendered pixels, time, and total output independently of the uploaded-byte limit.

2. Code quality/organization: points lost if the many endpoints, middleware, duplicated client/server normalization, and nine documents produce more framework than working logic. Points earned by a small dependency-injected pipeline, typed schemas, focused tests, and one readable request path.

## 6. Domain check

1. Encode the complete prescribed §16.21 text, including `GOVERNMENT WARNING:`, both numbered clauses, capitalization of “Surgeon General,” and both commas. 5. 6. “Malt beverages ABV optional federally” is incomplete. Under §§7.63 and 7.65 it becomes mandatory when alcohol derives from added nonbeverage flavors/ingredients, and state law can also require it. If retained, copy the current authorized lists and exceptions from [§5.203](https://www.ecfr.gov/current/title-27/chapter-I/subchapter-A/part-5/subpart-K/section-5.203) and [§4.72](https://www.ecfr.gov/current/title-27/chapter-I/subchapter-A/part-4/subpart-H/section-4.72), date the source, and test newly added sizes. Do not infer actual container capacity conclusively from OCR text.
9. Malt beverages have no analogous federal fixed-size list, but net-content expression rules still apply. “No standards of fill” must not become “no net-contents rules.”
10. Country-of-origin wording is not safely reducible to Parts 4, 5, and 7; customs marking rules may control. Keep it as application-versus-label comparison unless the relevant Title 19 provisions are also verified.

1. Decorative OCR: confidence is not field accuracy, and expected-value fuzzy search can conceal bad OCR. The Day-0 bake-off needs curved, condensed, outlined, gold-on-black, low-contrast, and mixed-case brands; report exact field recall, false matches, and latency—not mean OCR confidence.
2. Python wheels: ARCHITECTURE inherits Python 3.12 from PLAN; keep it. Enforce `requires-python ==3.12.*`, build Linux/amd64 in CI, and lock RapidOCR, ONNX Runtime, OpenCV, Pillow, and PDFium from that environment. Do not let a Windows Python 3.13 workstation define the lock.
3. ORT concurrency: `intra_op_num_threads=1` and `OMP_NUM_THREADS=1` may not disable all inter-op/provider pools. Verify actual process thread count and throughput at concurrency 1/2/3; a semaphore limits requests, not internal ORT threads.
4. Engine memory: one complete RapidOCR engine per worker may duplicate three model sessions. Measure resident memory after warm-up and under two simultaneous images before asserting that 1 GB works.
5. Coordinate mapping: preserve quadrilaterals, not only axis-aligned boxes; compose EXIF mirroring, rotation, crop, resize, deskew, and PDF-page transforms. Return normalized coordinates in one canonical oriented-image space and test all eight EXIF orientations plus CSS `object-fit`.
6. Client-side evidence crops may disagree with server orientation because browsers decode EXIF differently. Generate the displayed preview through the same canonical orientation or return a canonical preview asset.
7. USWDS without a build step is viable only by vendoring compiled `dist` CSS, JS, fonts, and images with their relative paths intact. Test sprite references, font URLs, CSP behavior, component JavaScript, and asset licensing; do not copy SCSS expecting it to work directly.
8. Azure Container Apps: explicitly configure external ingress, `targetPort`, CPU/memory pair, `minReplicas: 1`, startup/readiness/liveness probes, model-startup allowance, registry access, secrets, and revision traffic. Verify the configured cost instead of repeating the “~$10” estimate.
9. The §3 six-second deadline is per image, while Sarah’s expectation is results per application. A normal front/back application may run two OCR jobs serially or contend with batch work. Publish application-level p50/p95 under concurrent load.
10. Multipart limits are easy to apply after buffering. Enforce aggregate and per-file caps while streaming; multi-image `/verify` must not admit N × 10 MB unchecked.
11. Browser batch “resume is trivial” is overstated. It works only while the tab and file objects survive. A refresh loses extraction, pairing, notes, and decisions; state this plainly and test unload/export behavior.
12. Pairing is both ambiguous and potentially \(N \times M\). A warning-only back image may have no useful match signal. Require explicit/manual pairing before treating a grouped application as ready.
13. PDF rendering multiplies input size and exposes native parsing code. If retained, cap pages, rendered pixels, time, and total output independently of the uploaded-byte limit.

## 5. Reviewer's-eye check

1. Correctness/completeness: points lost for omitting producer/address and import origin, accepting an inexact warning, or falsely flagging valid wine/beer. Points earned by beverage-specific golden fixtures, expected-versus-found evidence, and a zero-false-pass warning suite.
2. Code quality/organization: points lost if the many endpoints, middleware, duplicated client/server normalization, and nine documents produce more framework than working logic. Points earned by a small dependency-injected pipeline, typed schemas, focused tests, and one readable request path.
3. Appropriate technical choices: local OCR, one container, baked models, and no egress earn points. Two hosts, PDF support, automatic fuzzy pairing, and unmeasured thread assumptions look like poor scope control.
4. UX/error handling: the three one-click samples, plain statuses, progressive batch table, and highlights earn points. Opaque auto-pairing, no obvious manual reassignment, excessive controls, or a result after five seconds lose them. Add an observed novice usability result, not a “mother test” checklist.
5. Attention to requirements: a trace from all five bold phrases to executable acceptance tests earns heavily. The current §12 DoD weakens that by omitting a hard deployed p95 gate and conditional producer/origin checks.
6. Creative problem-solving: evals, no-egress proof, evidence-to-pixels, and false-alarm measurement are strong differentiators. Publish an error analysis with representative failures and threshold rationale; otherwise the architecture reads as promises rather than engineering evidence.

## 6. Domain check

1. Encode the complete prescribed §16.21 text, including `GOVERNMENT WARNING:`, both numbered clauses, capitalization of “Surgeon General,” and both commas. TTB examples treat missing commas as corrections; do not run the generic punctuation-stripping normalizer over this check. Verify against [27 CFR §16.21](https://www.ecfr.gov/current/title-27/chapter-I/subchapter-A/part-16/section-16.21).
2. Section 10 misattributes “separate and apart” to §16.22; it is in §16.21. Section 16.22 covers legibility, contrast, capitalization/bold, compression, characters per inch, type size, and label attachment.
3. Section 10 is correct that only “GOVERNMENT WARNING” must be bold and the remainder may not be bold. The legal thresholds are 1 mm at ≤237 mL, 2 mm at >237 mL through 3 L, and 3 mm above 3 L, with corresponding 40/25/12 characters-per-inch maxima. Verify [27 CFR §16.22](https://www.ecfr.gov/current/title-27/chapter-I/subchapter-A/part-16/section-16.22).
4. Part 16 applies to beverages containing at least 0.5% ABV and intended for human consumption. “Mandatory on all alcohol beverages” is acceptable brief shorthand but should not become an unconditional domain rule.
5. Section 5’s wine rule needs precision: under Part 4, numerical ABV may be omitted for wine at 14% or less only when “table wine” or “light wine” supplies the designation; the practical COLA scope begins at 7%. Verify [27 CFR §4.36](https://www.ecfr.gov/current/title-27/chapter-I/subchapter-A/part-4/subpart-D/section-4.36).
6. “Malt beverages ABV optional federally” is incomplete. Under §§7.63 and 7.65 it becomes mandatory when alcohol derives from added nonbeverage flavors/ingredients, and state law can also require it. Verify [27 CFR §§7.63–7.65](https://www.ecfr.gov/current/title-27/chapter-I/subchapter-A/part-7/subpart-E).
7. Distilled spirits mandatory information includes name/address as well as brand, class/type, ABV, and net contents; some items have same-field-of-vision requirements. Section 12’s five-check DoD misses this. Verify [27 CFR §5.63](https://www.ecfr.gov/current/title-27/chapter-I/subchapter-A/part-5/subpart-E/section-5.63).
8. Standards-of-fill lists changed in January 2025. If retained, copy the current authorized lists and exceptions from [§5.203](https://www.ecfr.gov/current/title-27/chapter-I/subchapter-A/part-5/subpart-K/section-5.203) and [§4.72](https://www.ecfr.gov/current/title-27/chapter-I/subchapter-A/part-4/subpart-H/section-4.72), date the source, and test newly added sizes. Do not infer actual container capacity conclusively from OCR text.
9. Malt beverages have no analogous federal fixed-size list, but net-content expression rules still apply. “No standards of fill” must not become “no net-contents rules.”
10. Country-of-origin wording is not safely reducible to Parts 4, 5, and 7; customs marking rules may control. Keep it as application-versus-label comparison unless the relevant Title 19 provisions are also verified.

## 7. Top five

1. Replace §12 with a lean DoD: one host, concise docs, explicit batch pairing, and no PDF/standards-of-fill/procurement extras until the core is green.
2. Make the exact-warning path truly exact and verify §§16.21–16.22, including punctuation, both clauses, anchor bold/caps, non-bold body, applicability, and measurable format limits.
3. Add a hard acceptance gate for deployed end-to-end p95 under five seconds on a normal front/back application, including concurrent batch load.
4. Include producer/name-address and conditional import-origin comparison, and correct the wine and malt-beverage requiredness rules.
5. Fix the execution design before coding: one priority-aware OCR limiter, honest timeout semantics, bounded multipart handling, and a canonical tested coordinate system.
