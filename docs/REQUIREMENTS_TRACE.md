# Requirements trace

Every requirement in the brief, including the ones stated only inside the stakeholder interviews,
mapped to what the prototype does and where a reviewer can see it. Phrases the authors emphasized
in bold in the brief are marked **(emphasized)**.

| Source | Requirement | What the prototype does | Where to see it |
|---|---|---|---|
| Sarah **(emphasized)**: "If we can't get results back in about 5 seconds, nobody's going to use it." | Results for an application in about five seconds | OCR runs in-process on a small neural model; the images of one application are read in parallel; every result shows its own timing next to a "target: under 5 seconds" note. Latency is measured, not claimed. Known cases over the target on the deployed sizing: a sideways photograph (three reads) and an upload with no statement at all (one extra round of reads, `docs/LIMITS.md` item 13). | Any result's verdict box; `docs/EVAL.md`; `docs/LOADTEST.md`; README "Measured" |
| Sarah **(emphasized)**: "something my mother could figure out", "Half our team is over 50. Clean, obvious, no hunting for buttons." | Usable without training or instructions | One screen, two numbered steps, one big button. Three one-click samples show what the tool does before anyone uploads anything. Plain-language statuses shown as icon, word and color. U.S. Web Design System components, large targets, keyboard and screen-reader support. | Home screen; an observed usability test is reported in the README |
| Sarah **(emphasized)**: "handle batch uploads", "200, 300 label applications at once" | Batch processing | Batch screen: drop a folder of images and a CSV of application rows; rows stream in as they finish; filters, decisions, notes and export. Pairing by CSV column or filename prefix, manual assignment for leftovers. Tested at hundreds of images in the load test. | Batch screen, "Load a demo batch"; `app/static/batch.js`; `docs/LOADTEST.md` |
| Jenny **(emphasized)**: warning "has to be exact. Like, word-for-word" | Exact warning text check | Character-for-character comparison of every word and punctuation mark with 27 CFR 16.21 (verified from the eCFR API), ignoring only letter case, spacing next to punctuation, the style of quotation marks and a hyphenated line break, which the regulation leaves to typography (most approved labels print the statement in capitals, `docs/EVAL_REAL.md`). Only an exact match passes. A dropped comma, an OCR confusable or a moved word boundary is "Needs review" with a diff; a changed, missing or added word is a mismatch. A statement printed sideways along a label's edge is found by a sideways re-read on the single-label screen. | Warning card on any result; `app/pipeline/warning.py`; `tests/unit/test_warning.py` |
| Jenny: "the 'GOVERNMENT WARNING:' part has to be in all caps and bold" | Anchor capitalization and bold | Capital-letters check on the anchor as read. Bold is measured from the pixels of the statement's own lines (stroke thickness of the heading against the rest of its line, D-044 and D-045): a heading clearly heavier is a Match on the heading row; heading and body of the same weight is Needs review on both rows; print too small to measure is "Not checked" with the reason, so nobody assumes it was verified. Never a failure. | Warning card "Format checks"; `docs/EVAL.md`, `docs/EVAL_REAL.md` |
| Jenny: "Smaller font, different wording, burying it in tiny text" | Legibility and size | Wording differences are caught as above. Physical type size cannot be measured from an image without a known scale, so it is listed as a limitation rather than guessed. | `docs/LIMITS.md`; `docs/REGULATIONS.md` |
| Jenny: "'Government Warning' in title case instead of all caps. Rejected." | Title case detection | Anchor read as title case is flagged "Needs review" with the regulation cited; the "Problem label" sample demonstrates it. | Sample "Problem label" |
| Jenny: "images that aren't perfectly shot ... weird angles ... bad lighting ... glare" | Robustness to imperfect images | Measured rather than engineered: the engine handled rotation, blur, glare, low contrast, perspective and small text on the test corpus without special preprocessing; sideways images are recovered with a rotation retry. Unreadable images get a specific reason. | Sample "Phone photo"; `docs/OCR_EVAL.md`; `docs/EVAL.md` degraded tier |
| Dave: "'STONE'S THROW' on the label but 'Stone's Throw' in the application ... You need judgment." | Case-insensitive matching with human judgment | Case-only and accent-only differences are a Match with a note. Anything less certain is "Needs review" with the evidence crop, never an automatic rejection. The tool never approves or rejects. | Sample "Problem label" (brand row); `app/pipeline/match.py`; `tests/unit/test_match.py` |
| Dave: "Just don't make my life harder" and the 2008 phone system that created more work | Low false-alarm rate, no dead ends | False-alarm rate on clean artwork is measured and reported. Every error message says what to do next. | `docs/EVAL.md` |
| Marcus: "our network blocks outbound traffic to a lot of domains ... firewall blocked connections to their ML endpoints" | No dependence on outside services | OCR model files are in the repository; no downloads at build or run time; no CDN assets in the page. A test blocks every socket connection and runs a full verification. | `tests/integration/test_no_egress.py`; `app/models/MANIFEST.json`; `app/static/uswds/VERSION.txt` |
| Marcus: "standalone proof-of-concept", "not looking to integrate with COLA directly" | Standalone, integration-ready | Single container, no database. A versioned JSON API with an OpenAPI description is how a .NET COLA would consume it later. | `/api/v1/openapi.json`; `docs/APPROACH.md` "Path to production" |
| Marcus: "We're not storing anything sensitive for this exercise", "PII considerations, document retention" | No persistence | Images live in memory for one request. No database, no upload directory, no logging of label text or filenames. Batch state lives in the browser and the page says a refresh clears it. | `docs/SECURITY.md`; `app/security.py` |
| Marcus: "We're on Azure" | Deployable on their cloud | Deployed on Azure Container Apps; the container runs anywhere. | README "Deployment" |
| Brief: required label elements (brand, class/type, alcohol content, net contents, bottler name and address, country of origin, health warning) | Check the mandatory elements | Six comparisons plus the warning report. Bottler and origin are compared when the application supplies them; origin is required when the application is marked imported. The bottler line is taken apart as COLAs registers it (trade name, legal name, the name used on the label, city, state) and the city and state corroborate the name; class/type is a review item when the wording differs, because the application's class description and the label's permitted designation legitimately differ (D-041). | Checklist on any result; `app/pipeline/compare.py` |
| Brief: "exact requirements vary by beverage type (beer, wine, distilled spirits)" | Beverage-type awareness | Required beverage-type field. Alcohol statement rules differ for spirits, wine (table wine exception) and malt beverages; standards of fill differ for spirits and wine and do not exist for malt. | `app/pipeline/parsers.py`; `docs/REGULATIONS.md` |
| Brief: sample fields as strings, e.g. "45% Alc./Vol. (90 Proof)" | Accept application values as written | Fields are entered as written; the same parser runs on the application value and the label text and compares numbers (percent, proof, milliliters). | `tests/unit/test_parsers.py` |
| Brief: "We encourage you to create or source additional test labels" | Test corpus | A deterministic label generator produces front and back artwork for ten fictional products with degraded and defective variants and exact ground truth; 46 images are committed. | `tools/make_labels.py`; `tests/fixtures/labels/` |
